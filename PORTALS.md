**Fill all (experimental, optional draft saves):** one orchestrator with a `fillAll` adapter descriptor per mapped portal. Evidence is saved inventories plus synthetic E2E only: no live save has been run, and none of the live redirect or acknowledgement markup is verified.
- Bangor (`form-post`, `config/portals/bangor.js`): Personal Details, Contact Details, Finance, a single exact **Save and continue**, review/declaration paths as boundaries.
- Greenwich (`checklist-link`, `config/portals/greenwich.js`): starts at `bwskalog.P_DispIndex` or a section, binds the `appno` of the checklist and refuses a section link or form for another application. Recognised sections: Name, Employment and supporting information, Permanent and Mailing Address, Qualifications, Statistical Information, Previous or Current Education, Programme. It opens each by its checklist link (no `wsct` guessing), presses only the `submit_btn` named **Continue** that posts to that section's own `P_Proc*` page, and follows the response back to the checklist. Signature, **Application is Complete**, **Finish Later**, Search Address and Delete Record are never used; Referee Details stays manual because all its fields are blocked. Whether the live response is the checklist or the next section is unverified.
- Greater Manchester (`same-document-tab`, `config/portals/manchester.js`): fills the open data-entry tab among PD, CD, PI, QU, EX, PS, PA (links by `href`, tabs hidden for the course skipped) after its lazy body loads (20 s bound), validates only that panel, then presses `#but_save_and_cont` when the portal's next visible tab is also a data-entry tab, otherwise `#but_save`. A save counts only after a fresh "saved" acknowledgement observed after the click (plus the expected tab being active when continuing with `#but_save_and_cont`); a stale success message or a tab switch alone is not enough; an error message, a trusted click or keypress in the page, or an unconfirmed save stops the run. The Submission tab (`#but_submit`) is never entered. The save request and acknowledgement markup are unverified.
- Unmapped sites (`generic-post`): run only with activeTab access (staff open the toolbar button on that page; no host permission is added). A screen needs exactly one visible **Save and continue** (case, spacing and `&` variants) that is a native submit posting same-window to the same origin and the same application directory (parent path of the current URL; root-level paths are refused), honouring `<base>` and submitter overrides. Submission, declaration, payment, sign-in or account words in the destination or page, password fields, missing required values, validation messages and unchanged repeat screens stop the run; a screen is identified by route, heading and field names, never values, with a 12 screen limit. AJAX-only save buttons are not supported.
Additional Information, Education, Employment, Language (Bangor) and anything not listed stay manual.

For each supervised journey, record the exact origin, page matcher, fields filled, existing values skipped, fields with no CRM value, fields left for manual review, and a sanitized HTML fixture under `fixtures/<portal>/` (committed warranty) in addition to the synthetic pages in `e2e/fixtures/`.
